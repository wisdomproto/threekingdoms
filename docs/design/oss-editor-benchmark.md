## 1. 조사 범위와 신뢰도

이번에는 소개 페이지의 설명과 실제 코드가 확인되는 부분을 구분했다. LT-Maker는 공식 제작 매뉴얼과 저장소 README를 중심으로, 다른 주요 후보는 README·라이선스·선정한 소스 파일을 함께 확인했다. 뒤의 `[S번호]`는 문서 끝의 출처 목록에 대응한다.

**이번 조사에서 하지 않은 것:** 앱 설치·실행, 마우스/터치 사용성 실측, 프로젝트 전체 빌드, 성능 측정, 모든 파일·의존성에 대한 라이선스 감사. 공개 브랜치의 일부 파일을 확인했으며 커밋 SHA로 고정한 재현 가능한 코드 감사는 아니다. 따라서 “동작 확인” 대신 “코드에서 확인”, “공식 문서에서 확인”으로 표현한다.

**판단을 구분하는 방식**

- **확인:** 열람한 코드나 공식 문서에 근거가 있는 기능.
- **해석:** 확인한 구조가 우리 프로젝트에 주는 의미.
- **제안:** 앞으로 삼국지 프로젝트에서 구현하거나 시험할 설계. 현재 구현됐다는 뜻이 아니다.
- **미확인:** 앱 실행·추가 코드·라이선스 검토 없이는 확정할 수 없는 부분.

시장 규모, 사용자 수, 개발 기간 단축률, 광고수익은 이 조사로 추정하지 않는다.

## 2. 먼저 정정할 부분

### 2.1 현재 삼국지 프로젝트에는 이미 리깅 기반이 있다

`tools/rig-editor.html`에는 강체 컷아웃 방식의 리그 편집, 본·슬롯·이미지 부착, 키프레임, 타임라인 재생, 무기 교체를 다루는 코드가 있다. 메시 변형·IK를 갖춘 종합 애니메이션 툴과는 구별해야 하지만, “리깅을 처음부터 만들어야 하는 상태”는 아니다. [S01]

실행 쪽의 `apps/web/src/pixi/skeleton.ts`에는 본, 슬롯, 부착 이미지, 클립 모델과 순수 포즈 계산이 있다. 확인한 클립 이름은 `idle / move / attack / hit`다. `layers/SkeletonView.ts`에는 포즈·클립 조작 및 슬롯 부착물을 바꾸는 `setAttachment`가 있다. [S02][S03]

**따라서 기존 계획은 다음처럼 수정하는 편이 정확하다.**

```text
수정 전 사고방식
새 리깅 시스템과 새 리그 에디터를 만든다.

수정 후 사고방식
기존 리그 편집기 + Skeleton 모델 + Pixi 표현을 유지한다.
→ 프로젝트 에셋 관리와 연결한다.
→ 장비 외형과 스킨 조합을 연결한다.
→ 무기별 동작과 스킬 연출 선택을 확장한다.
→ 실제 전투에서 테스트하고 편집 화면으로 돌아온다.
```

전체 장비·스킨·스킬 변형이 이미 끝까지 연결됐다는 뜻은 아니다. 확인된 것은 리그·부착물 교체의 기반이다.

### 2.2 앞서 제시한 후보는 같은 종류의 제품이 아니다

SRPGcore는 **RPG Maker MV용 전투 플러그인**이고, Godot 예제는 **전술 RPG 데모**다. Project-Tactics의 전장 제작·공유 비전 역시 완성형 웹 저작도구가 확인됐다는 뜻은 아니다. “오픈소스 SRPG”라는 이름만으로 저작도구의 성숙도를 비교하면 안 된다. [S21][S23][S29]

## 4. LT-Maker — 가장 가까운 SRPG 제작 경험

### 확인한 내용

공식 가이드는 프로젝트 단위 저장, 클래스·유닛·아이템·스킬 데이터베이스, 리소스 관리, 레벨별 유닛 배치·영역·그룹·이벤트를 다룬다. 기본 맵 제작 튜토리얼은 **선택한 챕터를 F5로 테스트**하는 흐름을 안내한다. [S08][S09]

아이템 제작에서는 미리 구성된 무기 템플릿을 불러와 필요한 컴포넌트를 추가한다. 효과를 장수별 하드코딩으로만 처리하는 대신 데이터 조합으로 편집하는 참고 사례다. [S10]

### 우리에게 가져올 설계

**전역 정의와 챕터 배치를 구분한다.** 프로젝트의 ‘관우’는 고유 캐릭터 정의이고, 사수관에 배치된 관우는 그 정의를 참조하는 인스턴스다. 레벨·출격 좌표·시작 상태처럼 이번 전투에만 필요한 값은 배치에서 덮어쓴다.

이렇게 해야 한 챕터에서 레벨을 바꿨는데 전체 캠페인의 관우가 바뀌는 혼란을 줄인다. Inspector에는 `이 전투에서만 변경`과 `공통 캐릭터 편집`을 구별한다.

**템플릿은 완성 가능한 최소 조합을 제공한다.** 새 무기를 만들면 이름만 비어 있는 화면이 아니라, 사거리·기본 피해·사용 조건이 있는 ‘기본 근접 무기’에서 시작하게 한다. 스킬도 같은 방식으로 구성한다.

**챕터 테스트를 작업의 기본 동작으로 둔다.** 테스트 전에 현재 챕터·출격 상태·승패조건을 다시 여러 화면에서 설정하게 만들지 않는다.

### 그대로 따르지 않을 부분

공식 맵 가이드에서는 화면에 적는 목표 문구와 실제 승패 처리 이벤트가 별개다. 우리 도구에서는 가능하면 실제 승패 규칙을 중심에 두고, 기본 설명을 자동 생성하거나 문구와 규칙 불일치를 검사한다. ‘적장 격파’라고 써 놓고 실제 조건은 적 전멸인 실수를 줄이기 위해서다. [S09]

LT-Maker의 배포는 프로젝트/실행 파일을 만드는 데스크톱 경로다. 곧바로 우리 웹 런타임에 끼울 수 있는 TypeScript UI 컴포넌트라고 보지는 않는다. [S11]

## 5. RPGAtlas — 웹 저작도구의 내부 연결을 볼 후보

### 확인한 내용

`editor-state.ts`는 프로젝트·현재 맵·선택·도구 상태를 모으고, `persistence.ts`는 편집 후 저장 지연·가져오기·내보내기·오류 처리를 담당한다. `edit-scope.ts`는 변경 전 기준 상태와 편집 종료를 이용해 되돌리기 기록을 묶는다. [S13–S15]

`workspace.ts`의 F5는 저장 뒤 테스트를 열며, 브라우저 경로는 같은 출처의 별도 플레이 창으로 전달한다. 웹 배포 생성 코드도 존재한다. **이것은 제작·실행 연결의 근거이지, 클라우드 UGC 서비스가 완성됐다는 근거는 아니다.** [S16–S17]

### 우리에게 가져올 설계

1. **프로젝트 문서와 편집기 UI 상태를 구분한다.** 캐릭터·맵·이벤트는 문서에, 선택·줌·접힌 패널은 편집기 세션에 둔다.
2. **사용자가 생각하는 한 작업을 Undo 한 번으로 만든다.** 붓으로 여러 칸을 한 번 칠한 동작, 슬라이더 드래그, 유닛 이동을 각각 하나의 명령으로 묶는다.
3. **가져오기·저장·검증·테스트에 공통 데이터 접근 계층을 쓴다.** 각 도구가 자체 JSON 스키마를 조금씩 만들지 않는다.
4. **오류를 되돌아갈 수 있는 위치와 연결한다.** 참조가 깨진 장수·스킨·이벤트를 클릭해서 연다.

### 그대로 복사하지 않을 부분

브라우저 로컬 저장과 별도 창 전달을 그대로 최종 플랫폼 규격으로 삼지는 않는다. 다중 작품·여러 탭·공개 버전이 생기면 프로젝트/버전/세션별 이름공간과 저장 충돌 처리가 필요하다.

읽어들일 때 모르는 필드를 보존하는 것과 런타임이 그 명령을 지원하는 것은 다르다. **미지원 이벤트를 보존한 채 저장은 허용하되, 테스트·공개 단계에서는 실행 가능 여부를 별도로 판정한다.** 무시하고 성공으로 표시하면 안 된다. 스키마와 이벤트 타입은 이 구분을 검토할 출발점이다. [S18]

RPGAtlas의 코드를 가져오려면 GPL 조건을 선택적으로 무시할 수 없다. 같은 TypeScript여도 Pixi/React 기반 현재 프로젝트에 바로 붙는다는 의미는 아니다. [S12][S32]

## 6. LDtk — 전투 규칙과 맵 그림을 분리하는 참고 사례

LDtk는 엔티티 정의와 레벨 인스턴스를 JSON에서 구분하며, IntGrid는 의미 있는 정수 값으로 지형을 칠하는 방식을 제공한다. 자동 레이어는 그 의미 데이터 주변 조건을 보고 시각 타일을 배치한다. [S19][S34][S35]

**삼국지에 적용할 제안:**

```text
논리 지형: 평지 / 숲 / 산 / 물 / 성문
              ↓
이동 비용·진입 가능·전투 보정

동일 논리 지형 + 그림 테마
              ↓
타일·해안 경계·풀·나무·장식
```

제작자가 숲을 칠하면 기본 이동 규칙은 숲으로 유지하고, 그림은 테마에 따라 바뀌게 한다. 명화풍 배경으로 바꿨다고 숲의 이동 비용이 사라지면 안 된다.

현실적인 채택 경로는 **LDtk JSON을 현재 맵 형식으로 바꾸는 임포터** 또는 독립적으로 구현한 비슷한 편집 UX다. LDtk는 데스크톱 편집기이므로 전체를 웹 앱에 통째로 임베드하는 것이 간단하다고 가정하지 않는다. MIT 표기도 타일팩이나 사용자가 올린 에셋의 이용허락을 대체하지 않는다. [S20]

## 7. Sulis — 장비의 논리 슬롯과 외형 레이어

Sulis에는 실제 영역 편집기와 유닛·조우·트리거 관련 제작 코드가 있다. 인벤토리 데이터는 장착 슬롯과 아이템을, 외형 데이터는 머리·수염·몸통·손·망토·좌우 무기 등 이미지 레이어를 별도로 다룬다. [S24–S27]

**가져올 핵심은 ‘장비 하나 = 그림 하나’로 고정하지 않는 것**이다.

갑옷 한 벌은 몸통과 팔·다리 부착물을 함께 바꿀 수 있다. 망토는 앞/뒤 레이어가 필요할 수 있다. 게임 규칙상 하나의 `armor` 슬롯이어도 표현상 여러 부위의 묶음일 수 있다.

Sulis의 레이어 결합을 Spine 같은 메시 리깅·IK 구현으로 오해하면 안 된다. 우리에게는 기존 본 기반 시스템 위에 **외형 조합 규칙**을 만드는 참고 자료다.

Sulis README는 코드·일부 데이터의 GPL뿐 아니라 그림의 별도 조건을 안내한다. 일부 자산은 Sulis의 일부로만 배포하도록 제한된다. 엔진의 오픈소스 여부와 샘플 그림을 가져갈 수 있는지는 다른 문제다. [S24]

## 8. 나머지 후보에서 가져올 것과 빼야 할 기대

### 8.1 SRPGcore: 전투 이벤트의 언어

공식 설명상 RPG Maker MV의 편집 기능을 활용하는 플러그인이다. 코드에는 전투 시작, 아군/적군 턴, 턴 종료, 행동 후, 유닛 이벤트 등의 연결점이 있다. [S21][S22]

우리 도구에서는 다음처럼 번역할 수 있다. 아래 표기는 **제안**이지 기존 엔진에 확인된 API 이름이 아니다.

| 제작자 화면 | 내부 개념 예시 | 주의할 것 |
|---|---|---|
| 전투가 시작되면 | BattleStarted | 테스트 재시작 시 초기화 |
| 아군 5턴이 시작되면 | PhaseStarted + turn=5 | 턴과 진영 페이즈 구분 |
| 관우의 행동이 끝나면 | ActionResolved + actor=관우 | 애니메이션 종료와 구분 |
| 화웅이 쓰러졌을 때 | UnitDefeated + target=화웅 | 같은 사건 중복 실행 방지 |
| 이 지역에 들어오면 | UnitEnteredRegion | 이동 경로 중간/최종 칸 규칙 명시 |

플러그인의 태그·메모 필드·전역 번호를 그대로 초보자 UI에 복제하지 않는다. 조건 선택기와 행동 카드로 보여주고, 스키마·검증·실행기가 같은 명령 정의를 보게 한다. RPG Maker 본체는 이 플러그인의 MIT 라이선스로 제공되는 것이 아니다.

### 8.2 SRPG Construction Kit: 편집 대상 분류

실제 Unity 에디터 코드에서 장비 슬롯·카테고리·능력치 효과를 나누어 편집한다. 맵 내보내기 코드는 높이 구간을 파일로 직렬화한다. [S36][S37]

참고할 것은 “장비·행동 스킬·수식·상태이상을 각각 편집 가능한 자산으로 나눈다”는 설계다. Unity Editor API 의존 코드나 별도 맵 형식을 우리 TypeScript 웹 도구에 이식하는 비용은 따로 든다. 높이 기반 전투를 새로 도입해야 한다는 근거도 아니다.

README가 에디터와 라이브러리의 라이선스를 다르게 설명하므로 단일 허용 라이선스로 묶어서 재사용하면 안 된다. [S28]

### 8.3 Project-Tactics: 제작 플랫폼 비전과 현재 증거 구분

README에는 전장 제작·공유 방향이 있지만, 확인한 Tools 문서는 앱·샘플 생성/삭제 등 개발 보조 도구 중심이다. OpenTactica의 확인한 기본 상태 코드는 리소스·입력·상태 전환을 보여준다. [S23][S30][S31]

이번 확인만으로 완성된 GUI 저작도구의 프로젝트 저장 → 챕터 테스트 → 배포 흐름을 입증할 수 없다. 따라서 **“곧 가져다 쓸 완성형 제작 플랫폼” 후보에서는 우선순위를 낮춘다.** 프로젝트 전체에 그런 기능이 전혀 없다고 단정하는 것은 아니다.

### 8.4 godot-tactical-rpg: 데모와 저작도구 구분

저자가 완성형 프레임워크가 아니라 간단한 전술 RPG 예제라고 명시한다. 이동·공격·턴·카메라·기본 AI의 참고는 가능하나, 사용자가 캠페인을 만들고 배포하는 별도 저작도구를 제공한다는 근거는 아니다. [S29]

이미 자체 전투 엔진이 있는 지금은 구현 비교용 후순위다. 이를 쓰려고 전체 Godot 전환부터 시작하지 않는다.

## 9. 현재 삼국지 코드에 대응시키면

현재 저장소 README는 데이터, 헤드리스 엔진, 시뮬레이션, 웹 표현을 분리한 패키지 구조를 설명한다. 이 경계를 유지하는 것이 우선이다. [S04]

| 확인한 파일/영역 | 확인 사항 | 이 조사 이후의 권장 작업 |
|---|---|---|
| `tools/dashboard.html` | iframe 기반으로 여러 도구를 여는 통합 메뉴 | 화면 메뉴 통합을 넘어 프로젝트·선택·테스트 세션 전달 |
| `tools/stage-editor.html` | 맵·배치·조건 편집, 검증 후 저장, 필드별 직렬화 | 미완성 저장과 테스트 검증 분리, 알려지지 않은 필드 보존 테스트 |
| `tools/rig-editor.html` | 본·슬롯·부착물·타임라인 편집 기반 | 기존 기능을 Character Studio 안에 배치 |
| `pixi/skeleton.ts` | 리그 스키마·순수 포즈 계산 | 스키마 버전·호환성·외형 프로필 경계 정리 |
| `pixi/layers/SkeletonView.ts` | Pixi 표시·클립/포즈·부착물 교체 | 장비/스킨 해석 결과를 주입하는 어댑터 연결 |

근거: [S01–S06].

### 같은 화면처럼 보이는 것과 같은 프로젝트를 편집하는 것은 다르다

대시보드에서 여러 에디터를 열 수 있다는 것은 좋은 출발점이다. 다만 iframe 이동만으로 각 에디터가 같은 초안·리비전·선택 상태를 안전하게 공유한다고 볼 수는 없다. 현재 구조를 당장 모두 재작성하기보다 먼저 공통 프로젝트 읽기/쓰기와 테스트 전달 규약을 붙일 수 있다. [S05]

### 저장 무손실을 먼저 검사한다

확인한 스테이지 에디터는 `serializeStage()`에서 알려진 필드를 조립하고, 검증 상태에 따라 저장 버튼을 막는 흐름이 있다. 이 구조에서는 신규 스토리·장식·스킨 필드가 계속 늘 때 저장 범위를 놓치기 쉽다. [S06]

개선 전후를 논쟁하기보다 기존 스테이지를 입력한 회귀 테스트로 판정한다.

```text
원본 읽기 → 수정하지 않고 저장 → 재파싱
→ 편집 대상으로 삼지 않은 필드가 보존되는가?

이벤트만 변경 → 저장 → 재파싱
→ 스토리·장식·캐릭터 외형·알 수 없는 확장 데이터가 보존되는가?
```

이는 “모르는 명령도 실행한다”는 정책과는 다르다. 보존·실행 지원·공개 허용을 각각 판단한다.

## 10. Editor ↔ Playtest 통합 설계 제안

> **공유할 것은 프로젝트 규격과 해석기다. 실행 중인 게임과 편집기가 같은 가변 객체를 함께 수정하게 만드는 것은 아니다.**

기존 문서의 “동일 Project Store”를 구현할 때 이 구분이 필요하다.

```text
Project Draft                         Editor Session
캐릭터·맵·챕터·에셋·외형                선택·탭·카메라·Undo
        │                                  │
        ├── 저장/로컬 복구 ──────────────────┘
        │
        ├── 테스트용 검증 + 참조 자산 해석
        │              ↓
        │      Immutable Playtest Snapshot
        │      projectId / revision / chapterId / seed
        │              ↓
        │        Independent Runtime State
        │        병력·위치·턴·진행 중 이벤트
        │              ↓
        │        테스트 결과·선택 정보
        │              ↓
        └────────── Editor로 복귀

Project Draft → 공개 검증 → 불변 Release → 일반 플레이어
```

### 경계별 책임

| 영역 | 담당 | 하지 말아야 할 일 |
|---|---|---|
| 프로젝트 저장소 | 초안·리비전·에셋 참조·복구 | 실행 중 병력 변화 저장 |
| 편집 명령 계층 | 변경 기록·Undo/Redo·충돌 처리 | 각 화면이 문서를 제각각 변환 |
| 콘텐츠 해석기 | 참조·장비·외형·이벤트 정규화 | 게임과 미리보기에서 다른 해석 |
| 테스트 스냅샷 | 지정 초안의 불변 입력 | 나중 편집을 자동으로 섞기 |
| 전투 런타임 | 시드·명령에 따른 독립 상태 | 초안 캐릭터 능력치 직접 수정 |
| 공개 릴리스 | 버전 고정·자산 고정·회귀 확인 | 제작 중인 파일을 바로 서비스 |

### 저장 정책

- 미완성 프로젝트도 저장한다. 구조가 부분적으로 잘못됐으면 복구 가능한 초안 상태로 보관한다.
- “로컬 복구본 저장”과 “서버에 저장”을 서로 다른 상태로 표시한다.
- 프로젝트/사용자/초안/테스트 세션별로 저장 키와 접근 권한을 구분한다.
- 병합할 수 없는 다중 탭 변경은 사용자에게 보여주고, 조용히 마지막 저장으로 덮어쓰지 않는다.
- 공개 버전은 테스트 초안의 변경을 자동 수신하지 않는다. 기존 세이브의 버전 호환성 정책도 별도로 정한다.

### 현재 HTML 도구를 살리는 점진 통합

첫 단계에서는 에디터를 전부 React로 다시 쓰는 것보다 **공통 저장·검증·스냅샷 어댑터**를 두는 방법을 검토한다. iframe을 유지하는 동안에는 버전 있는 메시지 형식, 출처 검사, 세션 ID, 응답 확인을 둔다. 일반 플레이어에게 편집 API를 노출하지 않는다.

실제 작업성이 검증된 뒤 화면별로 공통 Creator Shell 안에 옮긴다. UI 프레임워크 전환 자체를 제품 목표로 삼지 않는다.

## 11. 이벤트·캐릭터·스킨 데이터의 편집 단위

### 11.1 정의와 인스턴스

```text
Character Definition: 관우
  기본 스탯 / 가능한 병종 / 기본 외형 / 사용 가능한 스킬

Stage Unit Instance: 사수관의 관우
  characterId 참조 / 레벨 override / 위치 / 소속 / 초기 장비

Runtime Unit
  현재 병력 / 행동 여부 / 버프 / 현재 칸
```

이 구분을 에디터에도 노출한다. 공통 정의를 바꾸면 영향을 받는 챕터·캐릭터 수를 보여준다. 일괄 변경은 미리보기와 Undo를 제공한다.

### 11.2 이벤트 정의의 진실의 원천

단일 명령 카탈로그에서 타입, 파라미터, 번역 이름, 기본값, 참조 검사, 허용 위치를 관리하는 방향을 제안한다. UI가 허용한 이벤트가 실행기에 없거나, 런타임 액션이 에디터에 없는 불일치를 줄인다.

카탈로그만으로 모든 런타임 로직을 자동 생성할 필요는 없다. 실행기는 각 명령의 구현을 연결하고, 테스트가 등록 누락과 버전 차이를 잡는다. 이벤트별 `한 번만 실행`, 재진입, 실행 순서, 실패 시 처리도 정의해야 한다.

### 11.3 게임 장비와 외형 장비

```text
Gameplay Equipment
공격력·사거리·장비 제한·스킬 사용 조건

Equipment Appearance
이미지·부착 슬롯·그립 보정·동작 계열·VFX

Skin
기본 외형의 선택적 교체 묶음
캐릭터 그림·의상·애니메이션·스킬 연출·음성
```

능력치가 같은 외형 스킨을 만들 수도 있고, 게임 장비가 외형 변경을 동반할 수도 있다. 둘을 하나의 필드로 섞지 않는다.

## 12. Character Studio — 기존 리그를 활용한 구현안

### 12.1 먼저 제공할 기능

**기본 제작자:** 캐릭터 선택 → 무기/갑옷 외형 선택 → 호환 동작 선택 → 공격 미리보기 → 현재 전투에서 테스트.

**고급 제작자:** 기존 본·슬롯 편집 → 부착 오프셋/앞뒤 순서 조정 → 동작 타임라인 → 스킬 연출 타이밍.

첫 공개판부터 완전한 Spine 대체 편집기를 만들지 않는다. 현재 강체 리그로 필요한 품질을 낼 수 있는지 대표 장수 한 명을 먼저 검증한다.

### 12.2 무기 교체는 그림 한 장 갈아끼우는 것으로 끝나지 않는다

호환성 정보에는 다음이 필요하다.

| 항목 | 필요한 이유 |
|---|---|
| rigId / schemaVersion | 다른 뼈대에 잘못 부착되는 문제 방지 |
| slot / attachment | 무기를 붙일 위치와 부착물 식별 |
| weaponArchetype | 검·창·활·언월도의 동작 구분 |
| gripOffset / facing | 손잡이 위치·좌우 방향 정합 |
| animationSet | 유효한 이동·공격 동작 선택 |
| fallback | 전용 동작 누락 시 계속 표시 |

이 이름들은 설계 예시다. 현재 스키마 필드라고 가정해서 바로 코드를 생성하지 않는다.

갑옷은 여러 본에 걸친 부착물 묶음일 수 있다. 말은 장비 아이콘 하나가 아니라 탑승자와 말의 합성 리그·동작 조합일 수 있다. 실제 기병 이동력 변화는 게임 규칙, 말의 외형 변경은 표현으로 분리한다.

### 12.3 스킨별 스킬 액션과 전투 판정

**스킬의 명중·피해·대상·상태이상은 엔진이 결정한다.** 타임라인의 `HIT` 또는 `impact` 표시는 이미 결정된 결과를 화면에 보여줄 시점이다.

```text
같은 seed + 같은 게임 상태 + 같은 명령
                 ↓
        엔진이 전투 결과/이벤트 생성
                 ↓
   외형 A: 일반 횡베기  / 외형 B: 용 연출 + 큰 베기
                 ↓
    동일한 피해·대상·상태, 다른 화면 연출
```

스킨 타임라인이 피해 계산을 다시 호출하게 하면 프레임 누락, 연출 건너뛰기, 배속, 반복 재생에서 전투가 달라질 수 있다. 표시 이벤트는 식별자를 가지고 중복 재생을 제어한다. 연출 실패 시 기본 표현으로 넘어가며, 이미 계산된 결과를 재적용하지 않는다.

### 12.4 미리보기와 실제 전투

현재 리그 에디터는 Canvas2D 미리보기 코드가 있고, 전투 표현에는 Pixi `SkeletonView`가 있다. 즉 “현재 이미 똑같은 렌더러”라고 단정해서는 안 된다. [S01][S03]

우선 포즈 계산·외형 조합·스킨 우선순위·이벤트 시간 해석을 공유한다. 가능하면 Character Studio에도 동일 Pixi 뷰를 넣는다. 그 전까지는 동일 입력에 대한 포즈와 캡처 비교로 차이를 잡는다.

### 12.5 Spine 도입은 옵션이지 선결조건이 아니다

메시 변형·IK·복잡한 동작 제작이 실제 요구로 확인되면 Spine 같은 외부 제작/런타임 도구를 별도로 평가할 수 있다. 공식 Pixi 런타임은 존재하지만 커스텀 런타임 라이선스 및 Editor 조건이 있고, 에디터·런타임 버전 호환도 확인해야 한다. 오픈소스 MIT 부품처럼 취급하면 안 된다. 특히 UGC 저작 서비스에서의 사용 범위는 계약 조건을 별도로 확인한다. [S33]

## 13. 재사용 방식과 라이선스 판단

이 절은 기술 도입 시 확인해야 할 체크리스트이며, 개별 서비스에 대한 법률 판단을 대신하지 않는다.

### 13.1 재사용은 네 가지로 나눠 결정한다

| 방식 | 예 | 기본 접근 |
|---|---|---|
| UX/개념을 보고 독립 구현 | LT-Maker의 챕터 중심 흐름 | 화면/코드를 복제하지 않고 요구사항화 |
| 파일 포맷을 어댑터로 지원 | LDtk JSON → 자체 맵 | 포맷 버전·필드 보존·데이터 권리 확인 |
| 코드 일부를 가져와 수정 | 특정 저장/검증 유틸리티 | 해당 파일·의존성 라이선스 준수 |
| 별도 툴/런타임을 묶어 배포 | 외부 편집기 또는 애니메이션 런타임 | 배포·소스 제공·상용 계약 조건 확인 |

### 13.2 GPL은 상업적 이용 금지가 아니다

GPL은 유료 판매를 허용하지만, 적용되는 코드를 수정·결합·배포하는 방식에 따라 라이선스 고지와 대응 소스 제공 등을 검토해야 한다. 독립된 작업물을 묶는 경우와 파생 작업물을 만드는 경우도 구별한다. [S32]

사용자에게 브라우저 코드가 전달되는 구조라면 “서버에서 운영하니 검토할 필요 없다”고 가정하지 않는다. 반대로 GPL 부품 하나를 본다고 플랫폼의 모든 데이터·게임 시나리오가 자동으로 GPL이 된다고 단정하지도 않는다. 배포 범위와 결합 방식을 실제 구성으로 검토한다.

사용자가 엔진 공개를 원한다는 점에서 GPL이 무조건 배제 사유는 아니다. 다만 **원하는 공개 정책과 라이선스가 요구하는 공개 범위가 맞는지** 먼저 결정해야 한다.

### 13.3 에셋은 별도 장부로 관리한다

코드와 그림·음악·폰트의 권리 정보를 분리한다. 공개 샘플 게임의 유명 캐릭터 그림이나 애니메이션이 들어있다고 곧바로 재사용하지 않는다.

패키지에 최소한 `제작자 / 출처 / 라이선스 / 수정 허용 / 상업적 이용 / 재배포 범위 / 의존 에셋`을 기록한다. 애매한 파일은 공식 게임과 기본 에셋팩에서 제외한다.

## 14. 첫 통합 검증: 사수관 한 챕터

다음은 새로운 대형 툴 전체가 아니라 **현재 삼국지 제작을 실제로 빠르게 만드는 최소 통합 검증안**이다. 장수 배치·턴 조건·수치는 예시이며 기존 시나리오의 확정 설정이 아니다.

### 제작자가 할 일

1. 삼국지 프로젝트에서 사수관 챕터를 열거나 템플릿으로 복사한다.
2. 관우와 화웅의 배치를 바꾸고, 이번 전투에만 적용되는 레벨 값을 수정한다.
3. 관우의 무기·갑옷 외형을 두 조합 중 하나로 바꾼다.
4. 같은 게임 스킬에 기본 공격 연출과 다른 스킨 연출을 연결한다.
5. 아군 5턴에 한 번만 발생하는 증원 이벤트를 추가한다.
6. 현재 초안으로 테스트한다.
7. 결과를 본 뒤 에디터로 돌아와 선택·줌·편집 이력을 유지한 채 수정한다.

### 통과 기준

| 검사 | 합격 조건 |
|---|---|
| 저장 안전성 | 읽기→쓰기에서 미편집·미지원 확장 필드 보존 |
| 미완성 저장 | 배치나 에셋 참조가 미완성이어도 초안 보존 가능 |
| 테스트 일치 | 방금 편집한 초안/챕터/장비 조합이 실행됨 |
| 상태 격리 | 전투의 병력·위치·사망이 원본 초안을 바꾸지 않음 |
| 복귀 | 선택·탭·지도 위치·Undo 이력이 유지됨 |
| 이벤트 | 설정한 턴에 한 번만 증원, 재시작 시 초기화 |
| 장비 표현 | 방향·그립·겹침·애니메이션 호환 오류를 잡음 |
| 외형과 판정 분리 | 동일 시드·명령에서 두 스킨의 전투 결과 동일 |
| 연출 실패 | 누락 클립·VFX에도 폴백으로 전투 진행 |
| 배속/건너뛰기 | 피해 중복·이벤트 누락·대기 교착 없음 |
| 공개 버전 | 제작 초안 변경이 기존 공개 게임에 섞이지 않음 |

원하는 속도나 성능은 목표 장치에서 실측해 정한다. 현재 조사만으로 “몇 배 빠름”, “몇 주면 완성” 같은 수치는 약속하지 않는다.

## 15. 개발 우선순위와 작업 항목

| 순서 | 작업 | 참고 후보 | 산출물 |
|---|---|---|---|
| 1 | 저장·재저장 회귀 테스트 | 자체 코드, RPGAtlas | 손실 필드 테스트·원본 보존 규칙 |
| 2 | 프로젝트 문서/세션/실행 상태 경계 | RPGAtlas, LT-Maker | 데이터 접근·스냅샷·복귀 계약 |
| 3 | 챕터 테스트와 공통 Inspector | LT-Maker | 현재 챕터 테스트, 정의/인스턴스 UI |
| 4 | 이벤트·아이템·스킬 템플릿 | LT-Maker, SRPGcore | 명령 카탈로그, 조건/효과 편집 |
| 5 | 기존 리그와 장비/스킨 연결 | 자체 리그, Sulis | Character Studio 최소 기능 |
| 6 | 지도 의미/그림 분리 강화 | LDtk | 타일 테마/자동 배치, 필요 시 임포터 |
| 7 | 스토리 연출과 전투 연결 | 자체 스토리 요구 | 전후 스토리·타임라인·독립 감상 |
| 8 | 클라우드 공개·UGC 운영 | 별도 제품 설계 | 릴리스·권한·신고·에셋 정책 |

6번은 기존 맵 제작 속도가 실제 병목일 때 앞당길 수 있다. 캐릭터 리깅의 전체 재작성이나 범용 메시 애니메이션 편집기를 선행 조건으로 두지 않는다.

### 개발 작업으로 넘길 때의 지침

- 위 순서는 구현 지시의 초안이다. 먼저 현재 브랜치·테스트·데이터 계약을 읽고 수정 범위를 확정한다.
- 공식 삼국지 제작에 쓰는 기능을 공용 도구에 반영하되, 기존 플레이가 깨지지 않게 점진 이행한다.
- 특정 오픈소스의 코드를 가져오기 전 라이선스 기록을 남긴다. “벤치마크”와 “코드 복사”를 구분한다.
- 새 패키지 수를 늘리는 것보다 하나의 챕터를 편집하고 실행하는 왕복을 먼저 완성한다.

## 16. 기존 문서에 반영할 정정 목록

이 보고서는 아래 변경의 근거를 제공한다. **Master Plan v2와 Design Guide v2 파일 자체는 이번 조사에서 수정하지 않았다.**

| 기존 표현/우려 | 수정 제안 |
|---|---|
| 리그·리그 에디터 전면 신규 | 기존 강체 리그·에디터·SkeletonView를 재사용하는 확장 |
| Edit와 Play가 동일 Store 사용 | 동일 콘텐츠 계약 + 불변 테스트 스냅샷 + 별도 런타임 상태 |
| HIT 이벤트와 피해 판정 연결 | 엔진의 권위 있는 결과를 연출 마커가 표시; 스킨이 계산 재호출 금지 |
| 갑옷은 armor socket 하나 | 다중 부위 외형 묶음 지원, 슬롯과 그림 레이어 분리 |
| Preview와 게임이 이미 동일 | 현재 경로 차이를 확인하고 포즈/해석/렌더링 공유 목표로 수정 |
| 기존 오픈소스 툴을 대부분 가져오면 됨 | 재사용 범위는 실제 구조·라이선스·적합성 확인 후 결정 |
| 모르는 필드 보존 = 실행 허용 | 저장 보존과 런타임 지원/공개 검증 분리 |

## 17. 최종 권고

**현재 삼국지 엔진을 유지한다.** SRPG 제작 경험은 LT-Maker, 웹 편집 구조는 RPGAtlas, 맵 데이터는 LDtk, 장비 외형은 Sulis에서 선택적으로 배운다. 캐릭터 본·부착물·기본 동작은 이미 가진 리그 기반에서 시작한다.

목표는 “오픈소스 편집기 여러 개를 한 화면에 모으기”가 아니다.

> **한 프로젝트에서 장수·장비·전장·이야기를 편집하고, 방금 바꾼 그대로 실제 삼국지 전투를 실행한 뒤, 잃어버린 작업 없이 돌아오는 제작 환경을 만드는 것.**
