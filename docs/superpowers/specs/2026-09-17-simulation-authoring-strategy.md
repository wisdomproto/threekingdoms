# 시뮬레이션 기반 저작도구 전략

**작성**: 2026-09-17 · **상태**: 방향 합의, 구현 미착수 · **관련**: master-plan §9·§16(유저 도구), CLAUDE.md §11(밸런스 자동화)

---

## 1. 문제 정의

플랫폼 로드맵(삼국지 → 도구 공개 → UGC)의 대상은 **기존·신규 mod 제작자**다.
그들이 20년간 쓴 저작도구가 못 해준 것을 해주는 것이 도구의 존재 이유다.

**기존 mod 저작도구의 구조적 한계**: 영걸전·조조전 mod 도구는 전부 바이너리 패처(헥스 에디터,
데이터 테이블 편집기)다. 값을 *바꿀* 수는 있어도 그 값이 무엇을 의미하는지 *평가할* 수 없다.
시뮬레이션할 엔진이 없기 때문이다.

그 결과 mod 제작자의 밸런싱 루프는 이렇다:

    수치 수정 → 게임 실행 → 손으로 플레이 → 스테이지당 30분 → "좀 어려운가?" → 반복

게다가 **자기 실력 하나로만** 테스트한다. 20년간 mod 밸런스가 극단적인(껌이거나 지옥이거나)
이유가 이것이다.

## 2. 핵심 논지 — 엔진이 곧 시뮬레이터

우리가 가진 것은 그들이 구조적으로 가질 수 없는 것이다. 전투가 시드 고정(CLAUDE.md §2-1)이라
수백 런을 수 초에 돌리고 난이도 라벨을 뽑는다. **나중에 붙이는 기능이 아니라 아키텍처 우위다.**

## 3. 이미 보유한 자산

§11 이 사실상 이 기능의 엔진이다. CLI 개발 도구로 존재할 뿐, 사용자 기능으로 노출하는 것은
대부분 UI 문제다.

| 보유 자산 (§11) | 에디터 기능으로 번역하면 |
|---|---|
| `classify` → HEALTHY/EASY/HARD/BRITTLE/IMPASSABLE | 저장 즉시 "이 스테이지 난이도: 적정" 판정 |
| `autoTune` 전력 예산 스캔 수렴 (§11-B) | "적정 난이도로 맞춰줘" 버튼 |
| `pathCostField` 연결성 검증 (§11-C) | 진행 불가 맵 자동 검출 — mod 최악의 버그 |
| `force` 전력 지표 (atk+def×병력) | 신규 장수 투입 시 "기존 로스터 대비 과함" 경고 |
| {정책 티어 × 레벨 오프셋} 매트릭스 | "초보는 못 깨고 숙련자는 깬다" — 난이도를 실력 축으로 분해 |
| `BASELINE_LABELS` 스냅샷 회귀 게이트 | **밸런스 CI** (아래 3-1) |
| `campaign-progression-cli` | 캠페인 전체 레벨 곡선 시뮬 (아래 3-2) |

### 3-1. 차별화의 핵심 — 밸런스 회귀 게이트

§11-A 의 회귀 게이트(전 스테이지 승리 검증 + 라벨 스냅샷)를 사용자에게 주면:

> mod 제작자가 병종 스탯 하나를 수정하면 **"3화·17화가 깨졌습니다"** 즉시 알림.

게임 밸런스용 CI다. 어떤 mod 저작도구도 제공한 적 없다. 100스테이지급 대형 mod 제작자에게는
"편해지는" 수준이 아니라 없던 능력이다.

### 3-2. 캠페인 전체 이월 시뮬은 이미 동작한다

`packages/sim/src/campaign-progression-cli.ts` 가 27스테이지를 통으로 돌린다.
그것도 실제 게임의 메타 스토어를 그대로 import 해서:

    initialMeta → selectRoster(챕터 게이팅) → autoFormation → applySortieToStage
      → 전투 → applyRosterProgress(레벨·경험치 이월) → markCleared → triggerDepartures

가장 어려운 부분(메타 상태 이월)이 끝나 있다. mod 제작자가 가장 많이 실패하는 지점은 단일
스테이지가 아니라 **캠페인 전체 페이싱**인데, 그것을 통으로 돌려볼 수 있다.

## 4. 트로이 증거 — 엔진은 이미 콘텐츠 중립

`apps/web/src/troia/content.ts` 에서 **22KB JSON 하나**(`packages/data/json/troia/first-battle.json`)가
stage·map·commanders·items·unitClasses·portraits·story·tactics 를 전부 공급하고, 엔진은 손대지 않은
`createBattle` 을 그대로 쓴다.

```ts
context = { data: {...gameData, commanders: content.commanders, items, unitClasses, ...}, stage, map }
```

삼국지 대신 트로이 전쟁이 같은 엔진에서 돌고 `/play/troia` 로 플레이된다.

**함의: "mod 포맷을 설계해야 한다"가 아니라 `first-battle.json` 의 모양이 이미 mod 포맷이다.**
CLAUDE.md §1 의 "2탄 엔진 재사용으로 제작비 30%"는 가설이 아니라 실증된 상태다.

## 5. 발견된 갭 3개

### 갭 A — 시뮬레이터만 삼국지에 하드코딩 (최우선)

`packages/sim/src/runner.ts:49-51`:

```ts
const map = opts.mapOverride ?? gameData.maps[s.mapId];
const ctx: BattleContext = { data: gameData, stage: s, map };   // ← 하드코딩
```

`RunOpts` 에 `mapOverride` 는 있으나 `dataOverride` 가 없다. 그래서 sim 은 troia 를 전혀 모른다
(`grep troia packages/sim/` → 0건).

**이것이 가장 수지맞는 한 수다.** 기존 `mapOverride` 패턴을 그대로 미러해 `dataOverride?: GameData`
를 추가하면 리포트 카드·autoTune·회귀 게이트·캠페인 시뮬 **전체가 임의 데이터팩에서 동작한다.**
트로이가 이미 존재하므로 **테스트 픽스처가 공짜**다.

### 갭 B — 경제가 전혀 모델링되지 않음 (편향 최대)

현재 캠페인 시뮬은 `items: [...u.equipped]` 로 **로스터 기본 장비만 들고 27스테이지를 완주한다.**
골드 수입도, 상점 구매도, 보물 획득(§10)도 모델에 없다.

즉 **시뮬이 실제 플레이어보다 체계적으로 약하다.** 실제 유저는 막간마다 장비를 산다. 이 편향은
한 방향으로만 작용해 **난이도를 일관되게 과대평가**한다. 현재 "건강 25 · 불가 0"은 *장비 없이도*
다 깬다는 뜻이므로 실제로는 더 쉬울 수 있다.

§7 의 `ItemSchema effects{move,atkPercent,spiritPercent,defensePercent,doubleStrike}` 가 이미 구현돼
있으므로, 골드→구매→장착을 메타 이월 루프에 끼우면 된다. 구조 난이도는 낮고 정확도 이득은 크다.

### 갭 C — 아키타입이 1종뿐

`autoFormation` 은 "authored 우선 후 로스터 채움" 하나의 전략만 구현한다. 정책도 greedy/naive 2종.

## 6. 정정 — 반복 전투 레벨링은 이미 차단돼 있다

`apps/web/src/meta/metaStore.ts:333`:

> Unique victories train reserves too; **replaying a cleared battle cannot farm levels.**

§10 "노가다 파밍 루트 없음"이 코드로 강제돼 있다. 따라서 "반복 전투로 레벨을 올려 공략" 아키타입은
시뮬레이션 대상이 아니라 **애초에 불가능한 플레이**다.

**이것은 오히려 이점이다.** 일반적인 mod 에서 "너무 어려움"은 노가다로 해소되므로 난이도 라벨이
무를 수밖에 없다. 여기서는 도달 가능한 전력이 상한으로 고정되므로, **시뮬이 "불가"라고 하면 진짜
불가다.** 파밍 금지라는 설계 결정이 시뮬레이션을 건전하게 만든다. 도구의 세일즈 포인트로 쓸 수 있다.

## 7. 플레이어 아키타입 모델

레벨 축은 "얼마나 갈았나"가 아니라 **"경험치를 어디에 줬나"**다
(§10 "행동 기반 경험치 — 막타 몰아주기 육성 유지").

| 축 | 아키타입 | 현재 상태 |
|---|---|---|
| 전술 실력 | 숙련 / 평범 / 초보 / 무모 | 2종 (greedy·naive) |
| 경험치 배분 | 에이스 몰아주기 / 균등 / 방치 | 미모델 |
| 편성 전략 | 상성 최적화 / 최고레벨 우선 / 초보(아무나) | 1종 (`autoFormation`) |
| 경제 운용 | 에이스 집중 장비 / 전원 조금 / 무구매 | **전혀 미모델** |
| 보물 회수 | 완주 / 주경로만 / 무시 | 미모델 |
| 패배 대응 | 재도전(전술 개선) / 포기 | 기본 중단 |

### 봇 티어 설계 원칙

티어를 **랜덤 열화**로 만들면 안 된다. "가끔 멍청한 수를 둔다"는 사람의 실수 양상과 다르다.
사람의 실력 차이는 주로 **어떤 정보를 무시하느냐**다.

| 티어 | 특징 |
|---|---|
| 숙련 | 상성·지형·협공 전부 계산, 반격 피해 고려, 필살 타이밍 관리 |
| 평범 (≈현 greedy) | 기대 피해 최대화, 반격은 대충, 지형 일부 |
| 초보 (≈현 naive) | 가장 가까운 적 공격, 상성·지형 무시 |
| 무모 | 전진 우선, 손해 무시 — 진행 불가 여부의 하한 탐지용 |

산출이 "HARD" 한 단어가 아니라 **"초보는 못 깨고 평범은 깬다"**가 되므로 제작자에게 훨씬 쓸모 있다.

## 8. 바닥과 천장

**시뮬이 보장하는 것은 바닥이지 천장이 아니다.**

- 측정된다: 클리어 가능 여부, 난이도, 진행 불가, 캠페인 페이싱, 데이터 변경 회귀
- 측정 안 된다: **이것이 재미있는가**

승률 87%인데 지루할 수 있다. 다만 **대부분의 나쁜 mod 는 천장이 아니라 바닥에서 실패한다.**
바닥을 자동으로 제거하는 것만으로 "양질 양산"의 대부분이 온다.

### 천장도 일부는 측정 가능하다

| 지표 | 잡아내는 것 |
|---|---|
| **긴장 곡선** | 턴마다 "여기서 이길 확률". 2턴에 승부가 갈리면 승률 70%여도 지루하다. 좋은 맵은 한동안 50% 근처를 유지하다 해소된다 |
| 선택 엔트로피 | 최적수와 차선수의 격차. 한 수가 항상 3배 좋으면 그것은 선택이 아니다 |
| 전략 다양성 | 서로 다른 아키타입이 *각자 다른 방식으로* 이기는가. 한 조합만 통하면 자물쇠지 전투가 아니다 |
| 시드 분산 | 너무 낮으면 작업, 너무 높으면 운 |

긴장 곡선은 구현 가능하다 — 턴마다 상태를 스냅샷 떠서 N번 롤아웃하면 승률이 나온다(체스 엔진의
평가 곡선과 같은 개념). 제작자에게 "이 스테이지는 3턴에 이미 끝나 있습니다"라고 말해줄 수 있다.

§7 Phase A 시드 RNG 가 도입되면 이 지표들이 전부 분포로 격상된다.

## 9. 리스크

1. **봇이 약한 고리** (최대 리스크) — §11-A 가 이미 자백하고 있다. BRITTLE 는 "그리디 봇 비단조
   아티팩트, 사람은 +2면 더 쉬움". **라벨이 틀리면 이 기능은 없는 것보다 나쁘다.** 제작자가 "적정"을
   믿고 배포했는데 실제로 불가능하면 신뢰가 한 번에 무너진다. 봇→사람 보정이 숨은 연구 과제다.
   해법 후보: 실제 플레이 기록(리플레이)이 쌓이면 봇 라벨을 사람 데이터로 캘리브레이션.

2. **UGC 는 법적 표면을 새로 연다** — 유저 업로드가 시작되면 일부는 반드시 영걸전 맵 추출본과
   코에이 스프라이트를 올린다. 현재는 없는 DMCA 대응 의무, 모더레이션, 신고 처리가 생긴다.
   "월 0~5만원" 비용 전제는 정적 배포 기준이므로 재계산 필요.

3. **스코프** — CLAUDE.md §15 "v1 범위(칼같이)"에 에디터는 없다.

## 10. 우선순위

1. **`dataOverride` 추가** (갭 A) — 수 줄. sim 이 범용화된다. 트로이로 즉시 검증 가능
2. **§7 Phase A 시드 RNG** — 라벨이 단일 결과에서 분포로 격상. "승률 87%±6"이 "HEALTHY"보다
   신뢰 가는 피드백이다. 즉 시드 작업이 에디터 가치를 직접 올린다
3. **경제 모델링** (갭 B) — 체계적 편향 제거
4. **편성·경험치 아키타입 + 봇 티어 확장** (갭 C)
5. **천장 지표** (긴장 곡선 우선)

### 공개 단계 (스코프를 터뜨리지 않는 경로)

| 단계 | 범위 | 법적 표면 |
|---|---|---|
| v1 | **내부 개발 도구로 제대로 만든다.** 단 공개 에디터가 될 수 있는 구조로(엔진/UI 분리, 스테이지=순수 JSON — 이미 그렇다) | 0 |
| v1.5 | 공유 없는 로컬 에디터 공개. 만들고 자기가 논다 | 0 |
| v2 | 공유·랭킹. DMCA·모더레이션 정식 도입 | 본격 |

**지금 결정할 것은 "v1 도구를 공개 가능한 구조로 짓는다" 하나뿐이고, 나머지는 미룰 수 있다.**
비용이 거의 들지 않는 옵션 매수다.

## 12. 경쟁 환경 — 시뮬레이터는 어디에 있나 (2026-09-18 조사)

조사 상세·출처 = `docs/design/oss-editor-benchmark.md` §18.

**창작자 저작도구에는 없다.** SRPG Studio(이 장르 최대 상용 도구)의 "Enemy Balance"는 성장률 기반 적 스탯 계산기이고, 테스트는 전부 수동 플레이다. LT-Maker 등 벤치마크 대상 전부 동일. 자동 밸런스 시뮬레이션은 **자사 게임을 만드는 스튜디오**(Prismata)와 **학계**에만 있다. 자리가 비어 있다는 것은 추측이 아니라 확인된 사실이다.

### 왜 비어 있나

1. **기술 전제** — 시뮬이 되려면 엔진이 헤드리스·결정론·고속이어야 한다. 렌더링과 결합된 도구에 나중에 얹을 수 없고 처음부터 그렇게 지어야 한다.
2. **경제성** — 도구 벤더의 고객(취미 제작자)은 필요한 줄 모르는 기능에 돈을 더 내지 않는다. 스튜디오는 자기 게임에만 만든다.
3. **큰 회사는 필요가 없다** — 라이브 게임은 출시 후 수백만 세션의 텔레메트리로 튜닝하는 편이 더 정확하다. 특히 F2P는 플레이어 전력에 상한이 없어(가챠·강화) "이 스테이지를 깰 수 있는가"라는 질문 자체가 성립하지 않는다.

**그런데 텔레메트리는 제작자에게 전이되지 않는다.** 만드는 중인 사람은 플레이어가 0명이다. 배포 전에 "깰 수 있나"를 알려면 시뮬레이션밖에 없다 — 정확히 mod 제작자의 상황이다.

### 우리의 "제약"이 곧 전제조건이다

| 시뮬 성립 조건 | 우리 근거 |
|---|---|
| 플레이어 전력에 상한 | §10 파밍 없음 (`metaStore.ts:333` 강제) |
| 장비 성능 확정 | §13 불가침선 — 확률 강화·랜덤 스탯 금지 |
| 전투 재현 가능 | §2-1 시드 고정 (순수 RNG 금지) |
| 전투와 표현 분리 | `@tk/engine` 헤드리스 |

각각 다른 이유로 정한 규칙인데 합치면 **"밸런스가 계산 가능한 게임"**의 조건이 된다. 이 해자는 도구만 베껴서는 따라올 수 없다 — 게임 설계 전체가 이 조건을 만족해야 한다.

### 경고

비어 있는 이유가 "아무도 생각 못 해서"만은 아니다. Prismata는 이 일에 스타크래프트 AI 대회 우승자를 투입했다. §9 리스크 1(봇이 약한 고리)이 실제로 어려운 문제라는 증거다. 다만 ①상태공간이 훨씬 작고(고정 편성 그리드 전투) ②필요한 건 *강한* 봇이 아니라 **중간 실력의 사람과 눈금이 맞는** 봇이라 문제의 성격이 다르다. PrismataAI의 hierarchical portfolio search는 봇 티어 설계의 참고 후보(라이선스 확인 선행).
